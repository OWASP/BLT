# User API Keys Design

## Goal

Replace the production-facing shared `X-BLT-API-Key` model with user-owned API keys while keeping JWT Bearer tokens as short-lived UI/session authentication.

## Current State

The Worker currently blocks most routes before the router unless a static shared key is supplied in `X-BLT-API-Key`. That is useful as a temporary gate, but it does not represent account ownership. The local auth foundation now returns JWT Bearer tokens after signin, and those tokens can be used to create and manage user-owned API keys.

## Authentication Roles

- JWT Bearer token: short-lived user session used by the homepage UI and auth/account-management routes.
- `X-BLT-API-Key`: long-lived programmatic access key generated by a signed-in user and associated with that user.
- Static public key / `BLT_API_KEY`: compatibility fallback only. It remains accepted temporarily, but docs and UI should move users to generated keys.

## Public Routes

These routes must be reachable without `X-BLT-API-Key`:

- `/`
- `/v2`
- `/health`
- `/v2/health`
- `/auth/signup`
- `/v2/auth/signup`
- `/auth/signin`
- `/v2/auth/signin`
- `/auth/verify-email`
- `/v2/auth/verify-email`

API-key management routes are exempt from `X-BLT-API-Key` but require a valid JWT Bearer token in the handler.

## Data Model

Add `user_api_keys`:

- `id`
- `user_id`
- `name`
- `key_prefix`
- `key_hash`
- `scopes`
- `is_active`
- `created`
- `last_used`
- `revoked_at`

The raw key is shown only once at creation. The database stores only a keyed hash. The key format is `blt_live_<random_secret>`.

## API

JWT required:

- `GET /auth/api-keys`: list the signed-in user's keys without raw secret or hash.
- `POST /auth/api-keys`: create a named API key and return the raw key once.
- `DELETE /auth/api-keys/{id}`: revoke a key owned by the signed-in user.

Generated API keys authenticate programmatic requests through:

```http
X-BLT-API-Key: blt_live_...
```

When a dynamic key authenticates, the Worker attaches `request.user_id` and `request.api_key_id` before dispatching to handlers. Existing write handlers can then associate created records with the authenticated user, and ownership enforcement can be expanded route by route.

## Homepage UI

The existing homepage should include:

- sign in form using `identifier` and `password`
- sign up form using `username`, `email`, and `password`
- signed-in state stored in `sessionStorage`
- API-key list/create/revoke controls visible after signin
- Try-it requests should include `Authorization: Bearer ...` when signed in and should prefer a selected generated `X-BLT-API-Key` when available

## Non-Goals

- Full tenant isolation for every existing table in this iteration.
- GitHub OAuth login.
- Fine-grained key scopes beyond storing the `scopes` column for future use.
