# BLT-CVE Protocol Specification

## Overview

The BLT-CVE protocol defines a standards-driven, machine-readable, cryptographically verifiable, decentralized vulnerability registry that operates entirely on static hosting (GitHub Pages) and automated CI/CD (GitHub Actions).

This document specifies the data format, ID scheme, validation rules, and operational procedures for the BLT vulnerability namespace.

---

## 1. Namespace

All vulnerabilities in this registry use the `BLT` namespace, distinguishing them from MITRE-issued CVE IDs. BLT IDs are **not** official CVEs; they are community-assigned identifiers within the OWASP BLT project.

---

## 2. ID Format

```
BLT-YYYY-NNNN
```

| Component | Description |
|-----------|-------------|
| `BLT`     | Fixed namespace prefix |
| `YYYY`    | Four-digit year of publication |
| `NNNN`    | Zero-padded sequential number (0001–9999) |

### Rules

- IDs **must** be unique within the registry.
- IDs are **immutable** once merged into `main`.
- IDs **must not** be reused, even after deletion.
- The year component **must** match the folder under `/cves/YYYY/`.
- The filename **must** be `BLT-YYYY-NNNN.json`.

---

## 3. Entry Format

Each vulnerability entry is a JSON file conforming to `/schema/blt-cve-schema.json`.

### Required Fields

| Field         | Type     | Description |
|---------------|----------|-------------|
| `id`          | string   | BLT-YYYY-NNNN identifier |
| `published`   | string   | ISO-8601 date-time of first publication |
| `modified`    | string   | ISO-8601 date-time of last modification |
| `title`       | string   | Short summary (10–200 characters) |
| `description` | string   | Full technical description (≥20 characters) |
| `affected`    | array    | One or more affected product objects |
| `severity`    | object   | CVSS score and vector string |
| `references`  | array    | One or more reference URLs |
| `reporter`    | string   | GitHub username or identifier |

### Optional Fields

| Field       | Type   | Description |
|-------------|--------|-------------|
| `signature` | string | Reserved for future cryptographic signatures |

### Affected Object

```json
{
  "vendor": "ExampleCorp",
  "product": "ExampleApp",
  "versions": "1.0.0 through 1.2.3"
}
```

### Severity Object

```json
{
  "cvss_score": 9.8,
  "vector": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H"
}
```

---

## 5. Validation Rules

The automated validator (`.github/workflows/validate.yml`) enforces:

1. Each JSON file in `/cves/**` **must** validate against the schema.
2. The `id` field **must** match the filename (e.g., `BLT-2026-0001.json` → `id: "BLT-2026-0001"`).
3. The year in `id` **must** match the containing folder (e.g., `cves/2026/`).
4. No two files may share the same `id`.
5. All required fields must be present and non-empty.

---

## 6. Index and Feed

### `/index.json`

Auto-generated by `scripts/build_index.py` on every merge to `main`. Contains a lightweight listing of all entries for programmatic consumption.

### `/feed.json`

Auto-generated alongside `index.json`. Contains full metadata (title, dates, severity) suitable for RSS-style polling.

---

## 7. Relationship to Official CVE Program

BLT IDs are **not** issued by MITRE and are **not** part of the official CVE program. They are community-assigned identifiers intended to supplement official CVE tracking for vulnerabilities that may not yet have an official CVE or for use within the OWASP BLT ecosystem.

When an official CVE is later assigned for the same vulnerability, the BLT entry should be updated to reference it in the `references` array.
